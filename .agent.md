## Specialized Knowledge

### Karvon Architecture
- **Messages flow**: User → Telegraf handler → Business logic → Supabase → Notifications back to user
- **State management**: In-memory wizards (brokerSessions, profileSessions, wizardSessions)
- **Regions & Routing**: Preset regions (REGIONS constant), dynamic route building
- **Roles**: DRIVER, BROKER, ADMIN with different menu options and capabilities

### Common Workflows
1. **Order Placement**: User starts /neworder → wizard steps (from/to/car/details) → insertOrder → matchAndNotifyDrivers
2. **Driver Signup**: User registers → upsertDriverProfile → setDriverStatus → notifications
3. **Broker Yuk (Load) Placement**: brokerSessions wizard → brokerMatching → distributeOrder → crosspostToDm
4. **Order Acceptance**: Driver sees notification → acceptOrder → markOrderTakenForOthers → dispatchReport

## Response Principles

### When Debugging
1. Check **database constraints first** — many issues stem from RLS or schema mismatches
2. Verify **session state** — wizards are in-memory; check session.txt for Telegram session validity
3. Review **order/driver status flows** — state transitions must be atomic (use Supabase transactions)

### When Adding Features
1. **Understand existing patterns** before writing new code — codebase heavily uses wizard pattern and async iterators
2. **Consider RLS implications** — Supabase auth context must match for security
3. **Test across roles** — same flow may behave differently for driver vs broker vs admin
4. **Plan notifications** — use lib/notifications.matchAndNotifyDrivers or custom notification builders

### When Discussing Implementation
- Refer to specific file paths and line ranges where relevant
- Explain the "why" of Karvon architecture, not just the "what"
- Highlight potential issues: race conditions, session persistence, RLS gotchas
